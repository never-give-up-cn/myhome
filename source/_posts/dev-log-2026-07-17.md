## 坑一：行业代码带着方括号来报到

{% img /img/posts/code-brackets.svg '"行业代码转换" "代码修复"' %}

### 背景

从第三方导入企业数据时，`test.json` 里的 `industryCode` 字段长这样：

```json
{"industryCode":"[154,302]"}
```

方括号包着逗号分隔的数字 ID。看起来像是当初序列化 JSON 数组时偷懒直接 `toString()` 了。

### 问题

现有代码里有一个 `getCode()` 方法，负责把这些 ID 转成对应的字母/数字行业代码（如 154 → C, 302 → 20），然后以 `C,20` 的格式存入数据库。

但它的清理逻辑只去掉了双引号：

```java
industryCode = industryCode.replace("\"", "").trim();
```

结果 `"[154,302]"` 去掉引号后变成 `[154,302]`，按逗号一拆，得到的是 `["[154", "302]"]`。`getIndustryCodeById("[154")` 里调了 `Integer.parseInt("[154")`，直接抛出 `NumberFormatException`，整条数据跳过，静默失败。

### 修复

```java
industryCode = industryCode.replace("\"", "").replace("[", "").replace("]", "").trim();
```

多一行 `replace`，世界清净了。

### 反思

这种「肉眼看不见但程序会炸」的数据格式问题，最好的防线其实是在解析 JSON 时就做类型校验——如果 `industryCode` 预期是数组，就应该解析成 `List<Integer>` 而不是留着字符串自己切。但历史代码已经跑了好几个版本，改解析逻辑影响面太大，在入口处做一层防御性清理是性价比最高的方案。

## 坑二：MariaDB 的 Sequence 引擎，MySQL 不认识

### 背景

要把一份从 MariaDB 导出的 SQL（大概 17 万行）导入到本地 MySQL 8.0。

### 问题

导到第 172140 行时炸了：

```
ERROR 1286 (42000) at line 172140: Unknown storage engine 'Sequence'
```

看一眼那行的建表语句：

```sql
CREATE TABLE `prt_industry_seq` (
  `currval` bigint NOT NULL,
  `nextval` bigint NOT NULL,
  ...
) ENGINE = Sequence CHARACTER SET = utf8mb4;
```

**`Sequence` 是 MariaDB 独有的存储引擎**，用来模拟数据库序列（Oracle-style sequence）。MySQL 8.0 虽然也支持序列（通过 `CREATE SEQUENCE` 语法），但它不是一个存储引擎——也就是说，MySQL 根本不认识 `ENGINE=Sequence`。

### 修复

全局替换一把：

```bash
sed -i 's/ENGINE = Sequence/ENGINE = InnoDB/' xmsr_assess_dev.sql
```

然后重新导入，顺利通过。

### 补充说明

`prt_industry_seq` 表在 MariaDB 里是用 Sequence 引擎来生成自增 ID 的。改成 InnoDB 后，这张表退化为一张普通表——如果后续有写入操作，需要确保业务代码不会依赖 Sequence 引擎的特殊行为（比如 `nextval` 的自动递增）。一般来说，改成 InnoDB 后配合 `nextval` 字段的 UPDATE + SELECT 也能实现类似效果，只是少了一些 MariaDB 提供的语法糖。

## 小结

两个坑都不复杂，但很有代表性：

- **第一个是数据格式兼容问题**——上游系统输出的数据和你预期的格式不一致，防御性编程在边界处是值得的。
- **第二个是数据库迁移兼容问题**——MariaDB 和 MySQL 虽然同源，但各自有私有特性，跨库迁移时不能想当然。
